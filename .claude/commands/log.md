---
description: 오늘 한 작업과 트러블슈팅을 정리한다
---

문서 **둘**을 갱신한다. 사용자가 고치기 쉽게 **초안**을 만드는 게 목적이다.

1. `docs/개발-로그.md` — 오늘 한 작업과 결정
2. `docs/trouble/YYYY-MM-DD.md` — 오늘 겪은 에러 (아래 「트러블슈팅」 절)

## 1. 먼저 실제로 뭘 했는지 파악한다

추측하지 말고 확인한다.

- `git log --oneline --since="6am"` — 오늘 커밋
- `git status --short` / `git diff --stat` — 미커밋 변경
- 대화 맥락에서 **어떤 갈림길에서 뭘 골랐는지**, **뭐에 막혔다 어떻게 풀었는지**

## 2. 「작업 기록」 절에 이 형식으로 추가한다

날짜 항목이 이미 있으면 거기에 이어 쓰고, 없으면 새로 만든다.

```markdown
### YYYY-MM-DD

- **한 일**: (한 줄. 파일 이름 나열 말고 결과로)
- **정한 것**: (선택지가 있었는데 하나를 고른 것 / 왜 / **틀리면 어떻게 티 나나**)
- **막힌 것**: (증상 → 원인 → 해결)
- **넘어간 것**: (궁금했지만 지금 안 판 것. 나중에 CS 공부 목록이 된다)
```

해당 없는 항목은 **뺀다**. 억지로 채우지 않는다.

## 3. 판단 기준

**"정한 것"이 가장 중요하다.** 면접에서 쓸 자산이 여기서 나온다.

- 갈림길이 **없었던** 작업(파일 생성, 오타 수정, 단순 적용)은 "한 일"에만 한 줄로
- 갈림길이 **있었던** 것만 "정한 것"에 쓰되, 반드시 **왜**와 **틀리면 어떻게 티 나나**를 같이
- "틀리면 조용히 틀리는" 종류면 특히 강조한다. 그게 실무에서 제일 무서운 버그다

**코드가 어떻게 동작하는지는 쓰지 않는다.** 그건 코드를 보면 된다. **왜 그렇게 했는지**만 쓴다.

## 4. 결정 기록 표도 확인한다

오래 남을 결정(스키마, 모델, 계약, 아키텍처)이라면 문서 위쪽 「결정 기록 > 확정」 표에도 한 줄 추가를 **제안**한다. 바로 쓰지 말고 사용자에게 물어본다.

## 5. 외부에 물어볼 게 생겼으면

BE·클라우드에 확인이 필요한 항목이 나왔으면 「외부에 물어봐야 하는 것」 절에도 추가한다.

## 6. 트러블슈팅 — `docs/trouble/YYYY-MM-DD.md`

오늘 **막혔다가 푼 에러**가 있으면 하루치 파일 하나에 모아 쓴다. 파일이 이미 있으면 `---` 구분선을 넣고 이어 붙인다. 에러 하나당 이 블록 하나다.

```markdown
# YYYY-MM-DD 오류명

## 🐞 에러 내용
- 실제 에러 메시지를 그대로. 무엇을 하려다 났는지

## 🔍 원인 분석
- 어떻게 원인을 좁혔는지(쓴 명령 포함) → 진짜 원인

## ✅ 해결 방법
- 당장의 조치 / 근본 해결 / 남은 후속 작업

## 회고
- 다음에 같은 일을 겪지 않으려면 뭘 바꿔야 하나
```

**판단 기준**

- **막혔다가 푼 것만** 쓴다. 오타 고친 것, 한 번에 성공한 것은 안 쓴다
- **원인 분석이 핵심이다.** "이렇게 고쳤다"보다 "어떻게 원인을 찾았는지"(어떤 명령으로 범인을 특정했는지)가 나중에 재사용된다
- **에러 메시지는 원문 그대로.** 나중에 같은 메시지를 검색해서 찾아올 수 있게
- 알고 보니 **정상 동작**이었던 경우도 쓴다. 왜 오해했는지가 배울 점이다
- **회고는 사용자 본인의 말로 바꾸도록 안내한다.** 초안은 주되, 여기가 가장 개인적인 부분이라고 알려준다

## 마지막

두 문서를 고친 뒤, **추가한 내용을 짧게 요약해서 보여준다.** 사용자가 바로 고칠 수 있게.
