## 프로젝트 한 줄 요약

책 추천 커머스 "북적북적"의 **AI 서버**. 커머스 백엔드(Spring + MySQL)와 분리된 FastAPI 마이크로서비스이고, 자기 소유의 PostgreSQL + pgvector를 쓴다. 커머스 데이터는 BE MySQL → AI Postgres **단방향 복제**로만 들어온다.

V1에서 만들 엔드포인트는 6개다.

| | 경로 | 하는 일 | LLM |
|---|---|---|---|
| ① | `POST /search` | 키워드 + 벡터 검색 결합(제목 완전 일치 우선) | 안 씀 |
| ② | `POST /embeddings` | 텍스트 → 벡터 (내부 전용) | 안 씀 |
| ③ | `POST /recommendations/chat` | 대화로 추천 카드 최대 3장 | **씀** |
| ④ | `GET /recommendations/feed` | 취향 프로필 기반 개인화 목록 | 안 씀 |
| ⑥ | `POST /preferences/profile` | 취향 프로필 생성·재계산 | 안 씀 |

⑤ 취향 기억 추출과 ⑦ 쇼핑 에이전트는 V2다. 지금은 신경 쓰지 않는다.

### 임베딩 모델 — multilingual-e5-small, 384차원 (2026-09-16 확정)

| 후보 | 차원 | 쿼리 p95 | 처리량 | 5만 권 적재 | |
|---|---|---|---|---|---|
| **multilingual-e5-small** | **384** | **5.8ms** | **151 docs/s** | **5.5분** | **채택** |
| bge-m3 | 1024 | 41ms | 18 docs/s | 45분 | 처리량 8분의 1 |
| gemini-embedding-001 | 3,072 | 573ms | 7.6 docs/s | 1.8시간 | 탈락 — pgvector 인덱스 한도 2,000 초과 |

**`vector(384)`가 DDL에 박힌다.** 나중에 차원을 바꾸면 `book_embeddings`와 `taste_profile`을 전량 재생성해야 하고, 특히 `taste_profile`은 **AI 혼자 복구할 수 없다** — 온보딩 원본과 취향 기억을 AI가 저장하지 않으므로 BE가 전 사용자에 대해 ⑥을 재호출해야 하고, BE가 보관 중인 옛 기억 벡터는 `dim` 불일치로 400이 난다. 바꾼다면 **운영 배포 전에** 끝내야 한다.

> 개발 중 재임베딩 비용 자체는 낮다(13만 권 약 15분). 비싸지는 건 운영에 유저 데이터가 쌓인 뒤다.

### 별점 경계 — ERD와 다르게 간다

BE가 `DECIMAL(3,1)` 0.5단위(0.5~5.0)라 AI도 `numeric(2,1)`로 받는다. 그러면 ERD·API 명세가 정수 1~5를 전제로 써둔 **취향 계산 경계를 다시 그어야 한다.**

| 신호 | 가중치 | ERD 원문(정수) | **실제 적용(0.5단위)** |
|---|---|---|---|
| 구매 | +3 | — | — |
| 리뷰 선호 | +2 | 4~5점 | **4.0 이상** (4.0·4.5·5.0) |
| 나의 도서관 담기 | +1 | — | — |
| 리뷰 중립 | 0 | 3점 | **2.5~3.5** (계산에 안 씀) |
| 리뷰 비선호 | −2 | 1~2점 | **2.0 이하** (0.5·1.0·1.5·2.0) |

비선호 리뷰는 centroid 재료에서 **빼고**(가중평균에 넣지 않음) 카테고리 점수만 깎으며, **그 책 자체는 추천에서 제외**한다. 이 규칙은 그대로다.

DDL의 CHECK는 **범위만** 건다(`rating BETWEEN 0.5 AND 5.0`). 0.5 단위까지 강제하면 원본에 예외값이 하나라도 있을 때 복제가 통째로 거부된다. 복제 사본은 원본 제약을 그대로 흉내 내기보다 느슨하게 받는 쪽이 안전하다.


패키지를 붙인다. ⑧ `/health`까지 가는 데 필요한 최소 구성이다.

|---|---|

| `pydantic-settings` | 환경변수를 한 곳에서 로딩. 클라우드가 이미 고정한 변수명을 그대로 받는다 |
| `asyncpg` | AI Postgres 드라이버 |
| `ruff` · `pytest` | **취향이 아니라 클라우드 CI 계약.** AI 리포의 PR 파이프라인이 `Lint → Test`라 둘 다 없으면 CI가 돌지 않는다 |

`.gitignore`에 최소한 이만큼은 넣는다.

```
.venv/
__pycache__/
.env
.ruff_cache/
.pytest_cache/
.DS_Store
```

> `.env`가 빠지면 BE→AI 서비스 토큰이 그대로 커밋된다. 클라우드 계약상 `.env.production`은 **서버 로컬에만** 두고 Git·이미지에 넣지 않는다.

### 2단계 — 로컬 DB

로컬에는 Homebrew PostgreSQL 17이 이미 돌고 있고 pgvector 0.8.6도 설치돼 있다. 네 줄이면 끝난다.

```bash
createdb bookjeok_ai_dev
psql -d bookjeok_ai_dev -c "ALTER DATABASE bookjeok_ai_dev SET timezone = 'Asia/Seoul'"
psql -d bookjeok_ai_dev -c "CREATE EXTENSION vector; CREATE EXTENSION pg_trgm;"
psql -d bookjeok_ai_dev -c "SHOW timezone" -c "\dx"
```

- **기존 `bookjeok_ai` DB는 건드리지 않는다.** pgloader 실증 데이터와 e5/bge 벤치 벡터(각 1,000행)가 들어 있다
- `ALTER DATABASE ... SET timezone`은 한 번만. 이후 모든 연결이 KST로 시작한다
- 확장은 **DB마다 따로 켜야 한다**(설치는 서버 전체, 활성화는 DB별). 새 DB를 팔 때마다 필요
- `vector` = 벡터 저장·유사도 검색, `pg_trgm` = 한국어 부분 일치 검색

운영은 컨테이너(`pgvector/pgvector:pg17`)로 가지만, ③ 챗봇까지 붙인 뒤에 옮겨도 늦지 않다.

### 3단계 — 스키마

`db/migrations/001_init.sql` 하나로 시작한다. 내용은 **ERD 명세서 §2·§3을 그대로** 옮기면 된다.

쓸 때 놓치기 쉬운 것:

- 확장 두 개를 먼저 켠다(위에서 이미 켰다면 `IF NOT EXISTS`)
- 시각 컬럼은 전부 `timestamptz`. `timestamp`나 `DATE`는 쓰지 않는다 → 아래 "알아 두면 덜 아픈 것들"
- `book_embeddings.book_id`는 `v_books(book_id)` **진짜 FK에 `ON DELETE CASCADE`**
- 키워드 인덱스는 `v_books`의 `title`·`author`·`description`에 `to_tsvector('simple', ...)` + pg_trgm
- 벡터 인덱스는 HNSW에 `vector_cosine_ops`
- **`v_user_reviews.rating`은 `numeric(2,1)`로.** ERD는 `int`지만 BE가 `DECIMAL(3,1)` 0.5단위라 정수로 받으면 3.5점이 뭉개진다. 대신 취향 계산 경계를 4.0↑/2.0↓로 다시 긋는다
- **이력 3종에 PK를 임의로 걸지 않는다.** ERD가 명시하지 않았고, `(user_id, book_id)` 유니크를 걸면 재구매 행이 조용히 유실된다

쓰고 나면 `TRUNCATE v_books CASCADE`를 일부러 한 번 때려 보면 좋다. 임베딩이 전량 날아가는 걸 눈으로 보면 BE에 복제 방식을 요구할 때 근거가 생긴다.

`nl_sellable.jsonl`·`d4l_book.jsonl`은 원재료(국중 원본·정보나루 응답)라 필요 없다. `cat_books.jsonl`이 둘을 합친 완성품이고 **필드 이름이 ERD `v_books` 계약과 그대로 맞는다.**

**벡터 검색 대상이 23%뿐이다.** 나머지는 키워드 검색으로만 잡힌다. 고장이 아니라 API 명세 ②에 이미 규정된 동작이지만("`description`이 없는 도서는 벡터 검색 대상에서 빠지고 키워드 검색으로만 조회된다"), 검색을 테스트하다 "왜 벡터 결과가 적지?" 할 때 원인을 알고 있어야 한다. 대기분은 며칠 뒤 새 스냅샷에서 채워진다.

임베딩 소요는 133,732권 기준 **약 15분**(e5-small 151 docs/s). 전량 채워지면 약 64분.

1. **임시 테이블에 통째로** — `stg_cat_books(data jsonb)` 같은 것에 가공 없이 붓는다

## 알아 두면 덜 아픈 것들

**FastAPI 기본 에러가 계약을 깬다.** `HTTPException`은 `{"detail": ...}`를 내보내는데 계약은 `{"message": ..., "data": null}`이다. 검증 실패도 기본 422인데 계약은 400 `invalid_request`다. 예외 핸들러를 갈아끼우기 전까지 **모든 에러 응답이 규약 위반**이다. ⑧ 만들 때 이것부터 잡는다.

**`computed_at`이 뭔지 먼저 알아야 한다.** `taste_profile`의 컬럼인데 이름과 달리 "계산한 시각"이 아니라 **"이 프로필이 반영한 이력 중 가장 최근 것의 시각"** 이다.

취향 프로필은 ⑥을 호출할 때만 갱신되는데 ③④는 그 사이에도 돈다. 그래서 ③④는 "프로필에 안 들어간 최신 이력"을 그 자리에서 추가로 가산하는데, **어디부터가 안 들어간 건지**를 알려주는 경계선이 `computed_at`이다. 이 시각 이후의 이력만 더한다.

"계산 시각"이 아닌 이유는 복제 지연 때문이다.

```
14:00  책 A 구매            (BE MySQL 기록)
14:03  ⑥ 재계산 호출        ← 복제가 아직 안 와서 A를 못 봄
14:05  복제 도착            (AI DB에 purchased_at=14:00 행 생김)
```

`computed_at`을 계산 시각(14:03)으로 두면 → ③④가 "14:03 이후만 가산" → A(14:00)는 제외 → **프로필에도 없고 가산에도 없어 영구 누락.** 반영 시각(13:30)으로 두면 A가 포함된다.

**그래서 `DATE`(날짜만)는 쓸 수 없다.** 같은 날 안의 순서를 구분할 수 없어서, 부등호를 어느 쪽으로 해도 틀린다.

- `>` 로 하면 → 프로필 계산 **뒤에** 산 책이 같은 날짜라 제외됨 → **누락**
- `>=` 로 하면 → 프로필에 **이미 들어간** 책이 같은 날짜라 포함됨 → **이중 반영**

덤으로 `/health`의 `replication_lag_seconds`(초 단위)도 만들 수 없고, 신선도 예산(5분)도 판정이 안 된다. 복제가 끊겨도 응답은 전부 정상 200으로 나가기 때문에 **`replication_lag_seconds`가 복제 중단을 감지할 유일한 채널**인데, 그게 사라진다.

**타임존은 KST로 통일하되 타입은 `timestamptz`.** 한국은 서머타임이 없어 KST = UTC+9 고정이라 통일만 되면 논리가 다 성립한다. 위험한 건 타임존 선택이 아니라 **타입 선택**이다 — `timestamptz`는 Postgres가 내부적으로 UTC 정규화해 주지만, `timestamp`(tz 없음)를 쓰면 어떤 값은 KST 어떤 값은 UTC로 섞이는 순간 조용히 깨진다.

**`X-Degraded`는 값이 둘뿐이다** — `keyword-only`(①), `rule-only`(④). 복제 지연이나 행 부재에는 **붙이지 않는다.** ③은 헤더가 아니라 본문 `data.degraded`로 알린다(스트리밍이라 200 헤더가 먼저 나가므로).

**커서**는 검색어·필터·정렬·축소모드를 해시로 함께 서명해야 한다. 안 그러면 "발급 시점과 다르면 410" 규약을 구현할 수 없다. 유효기간 30분.

**`dim` 검사는 호출하는 쪽 책임이다.** ② 응답의 `dim`을 확인하고 저장한다. 차원이 같은 모델로 바꾸면 검사를 통과하고 옛 벡터와 조용히 섞인다.

**이력 3종에 PK를 임의로 걸지 않는다.** ERD가 PK를 명시하지 않았다. `(user_id, book_id)` 유니크를 걸면 재구매 행이 조용히 유실될 수 있다. → BE 확인 항목.

### BE 파트

2026-09-16에 [1단계 테이블 명세서](https://github.com/100-hours-a-week/KTB4-13th-wiki/wiki/%5B1%EB%8B%A8%EA%B3%84%5D-%ED%85%8C%EC%9D%B4%EB%B8%94-%EB%AA%85%EC%84%B8%EC%84%9C)를 확인해 상당수가 풀렸다.

**핵심 결론: BE를 그대로 따라가도 AI는 안 깨진다.** 전부 복제기/시드 스크립트 계층에서 흡수된다. 계약면을 "복제 수단"이 아니라 "테이블 이름 + 컬럼 집합"으로 정의해 둔 덕이다.

**확인된 사실 (→ 번역 규칙만 정하면 됨)**

| 항목 | BE 실제 | AI 계약 | 그대로 따르면 |
|---|---|---|---|
| 삭제 | **소프트 삭제** (`deleted_at` + `active_flag` GENERATED) | FK CASCADE 전제 | **오히려 이득.** 행이 안 지워지니 임베딩이 CASCADE로 날아갈 일이 없다. 조회에 `WHERE active_flag = 1` 한 줄 추가 |
| 도서 정보 | **두 테이블.** `books`(서지) + `items`(가격·재고) | `v_books` 하나 | 복제기가 조인. 한 책에 item이 여러 개일 수 있어 **대표 item 선정 규칙 필요** |
| 가격 | `items.sale_price`·`discounted_price` 둘, `DECIMAL(19,2)` | `price int` (할인 후) | `discounted_price` → 정수 캐스팅. 원화라 소수점이 사실상 0 |
| 재고 | `stock_quantity` + `status` | `in_stock bool` | `stock_quantity > 0 AND status = 'ACTIVE'` 파생 |
| 시각 | **`DATETIME(6)`** (TIMESTAMP 아님) | `timestamptz` | 시간대 정보가 없는 벽시계 값. BE가 `TZ=Asia/Seoul`이라 **KST가 들어있다** |
| 별점 | `rate DECIMAL(3,1)`, 0.5~5.0 0.5단위 | `rating int 1-5` | **AI 스키마를 `numeric(2,1)`로 바꾸고 경계를 다시 긋는 게 낫다** (예: 4.0↑ 선호 / 2.0↓ 비선호). 정수 캐스팅하면 정보 손실 |
| 책소개 | `description VARCHAR(255)` | `text` | **임베딩 재료가 255자로 잘린다.** 품질 저하지만 동작은 함 → 일단 보류 |
| 구매 시각 | `orders.paid_at`. 구매확정은 별개(7일 후 자동) | `purchased_at` | 어느 쪽이든 동작. `paid_at` 사용 |

**아직 열린 것**

- **④ 홈 피드가 `GET`으로 바뀐 것을 BE에 통보** — 2026-09-16 변경. BE가 POST로 부르면 405다. 요청 본문이 아니라 **쿼리 파라미터**로 받으며, `next_cursor`는 URL 인코딩해서 실어야 한다
- **`order_items` 테이블이 실제로 있는가** — 위키 요약에 안 나왔다. 정말 없으면 "누가 어떤 책을 샀는지"를 알 수 없어 `v_user_purchases`를 만들 수 없고, 취향 신호 중 가장 큰 항(+3)이 통째로 날아간다. **원문에서 직접 확인할 것**
- **`reviews.target_id`가 book인가 item인가** — item이면 book 매핑 필요
- **복제 방식** — 행 단위 upsert/delete여야 함(아래 실측 근거). TRUNCATE 후 재적재·DROP 후 재생성 불가
- **이력 3종 PK 유무** — 재구매가 가능한지
- **대표 item 선정 규칙** — 한 책에 종이책/전자책 등 여러 item이 있을 때
- **`category` 정규화 책임** — 문자열 정확 일치로 동작하므로 NFC 정규화·공백 처리를 누가 할지
- **탈퇴 시 `taste_profile` 삭제 시점** — 비즈니스 정책상 **7일 복구 기간**이 있다. 탈퇴 신청 시점에 지우면 복구한 유저의 프로필이 날아가므로 **탈퇴 완료(7일 후)** 여야 한다

**비즈니스 정책에서 알게 된 것**

- **온보딩이 필수**이고 완료 전엔 카탈로그 접근이 막힌다 → `cold_start`가 예상보다 훨씬 드물 것
- **리뷰는 탈퇴 후에도 남는다** (작성자 "탈퇴 회원") → `v_user_reviews`에 탈퇴 유저 행이 남을 수 있음
- 행동 데이터 90일 보관, 탈퇴 시 온보딩 응답 삭제

## 팀 Git 컨벤션에서 AI가 챙길 것

전체는 팀 위키의 "Git 협업 컨벤션" 참고. AI 파트에만 해당하는 것만 적는다.

- **브랜치** `feature|fix|hotfix|refactor|chore|docs/<issue>-<slug>`. main 직접 push 금지, **Squash Merge만**, 승인 1명, 자기 PR 자가 승인 불가
- **커밋** `<type>: <summary>`. 저장소 이름을 scope로 쓰지 않는다(`feat(backend):` ✗). 마침표 없음
- **PR 400줄 권장** — `uv.lock` 같은 Lockfile은 기준에서 **제외**된다
- **모델·프롬프트를 바꾸는 PR에는** Provider, Model ID, **Prompt Version**, **고정 Dataset 검증 결과**, 응답 시간·비용 변화, Timeout·Fallback 영향을 적어야 한다
  → **e5-small vs bge-m3 결정이 정확히 이 PR이다.** recall@10을 잴 때 **고정 질의 세트**를 만들어 둘 것. 나중에 모델을 또 바꿀 때 같은 세트로 재야 비교가 된다
- **Prompt Version 개념이 필요하다** — ③ 챗봇 프롬프트에 버전을 매겨 릴리스 메타데이터로 기록. 프롬프트만 바꿔도 추천 품질이 달라진다
- **구조화 로그에 `Release SHA`와 `Level`** 추가. Release SHA는 ⑧ `/health`의 `version`(커밋 해시 7자)과 같은 값이라 한 곳에서 꺼내 쓴다
- **벡터 차원 변경은 단독 배포** — "Column 삭제와 대량 데이터 변환은 일반 배포에서 분리". 384→1024는 두 테이블 전량 재생성이라 기능 배포에 섞으면 안 된다
- **스키마 변경은 반드시 Migration 파일로.** 운영 DB 수동 DDL 금지
