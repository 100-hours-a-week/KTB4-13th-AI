# 2026-09-16 Address already in use

## 🐞 에러 내용
- `uv run uvicorn app.main:app --reload` 실행 시 `[Errno 48] Address already in use`
- 8000 포트로 서버를 띄울 수 없었다

## 🔍 원인 분석
- `lsof -nP -iTCP:8000 -sTCP:LISTEN`로 확인하니 다른 Python 프로세스가 8000을 잡고 있었다
- `ps`로 명령줄을 보니 **이틀 전(1일 23시간 전) 띄워둔 `llm/bench` 임베딩 벤치마크 서버**였다
- 벤치마크가 끝난 뒤 껐다고 생각했는데 실제로는 계속 살아있었다

## ✅ 해결 방법
- 당장은 `--port 8001`로 우회해서 진행
- 근본 해결은 점유 중인 프로세스를 종료하는 것 (`kill <PID>`)
- **운영 포트가 8000으로 고정**이라(클라우드 compose 계약) 로컬도 8000을 쓰는 게 맞아서 나중에 정리 필요

## 회고
- 서버를 끌 때 "정말 꺼졌는지" 확인하는 습관이 없었다
- 확인은 한 줄이면 된다: `lsof -nP -iTCP:8000 -sTCP:LISTEN` — 아무것도 안 나오면 비어 있는 것
- 에러 메시지가 "누가 쓰고 있다"까지만 알려주지 "누가"는 안 알려준다. **범인을 찾는 명령을 아는 게 해결의 절반**이었다

# 2026-09-16 brew services 상태 불일치

## 🐞 에러 내용
- 앱 시작 시 `ConnectionRefusedError: [Errno 61] Connection refused` → `Application startup failed`
- `psql` 접속도 실패: `"/tmp/.s.PGSQL.5432" 소켓으로 서버 접속 할 수 없음`
- 그런데 `brew services start postgresql@17`을 하면 **"already started"** 라고 나왔다

## 🔍 원인 분석
- `brew services list` 확인 → 상태가 **`none`** (started가 아님)
- `pgrep`으로 확인 → **postgres 프로세스가 실제로 없었다**
- 앞서 실험으로 `brew services stop`을 했는데, brew가 관리하는 상태 정보와 실제 프로세스 상태가 어긋난 상황이었다
- `start`는 "이미 등록돼 있다"고 판단해 아무것도 안 하고, 실제로는 안 떠 있는 채로 남았다

## ✅ 해결 방법
- `brew services restart postgresql@17` → 정상 기동
- `pg_isready`로 확인 (`접속을 받아드리는 중`)

## 회고
- **도구가 하는 말보다 실제 상태를 믿어야 한다.** "already started"를 곧이곧대로 받아들여서 한참 헤맸다
- 확인 순서를 알아두면 빠르다: `brew services list` → `pgrep` → `pg_isready`
- 앱이 `ConnectionRefusedError`로 안 뜬 건 사실 **정상 동작**이었다. DB 없이는 시작을 거부하도록 만든 설계대로 움직인 것 — 오히려 "문제를 일찍 알려준" 경우였다
