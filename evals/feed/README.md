# ④⑥ 홈 추천 평가용 가상 사용자 묶음

홈 추천(`GET /recommendations/feed`)과 취향 프로필(`POST /preferences/profile`)을 고칠 때 전후를 견주는 데 쓰는 고정 묶음입니다. 두 기능은 결과가 틀려도 오류가 나지 않아서, 같은 사용자로 다시 재 보지 않으면 나아졌는지 알 수 없습니다. 배경은 [#364](https://github.com/100-hours-a-week/KTB4-13th-AI/issues/364)와 [#365](https://github.com/100-hours-a-week/KTB4-13th-AI/issues/365)에 있습니다.

묶음(`cases.json`)과, 묶음을 돌려 채점하는 실행기(`run.py`, `scoring.py`)가 있습니다. 통과·실패는 아직 매기지 않고 숫자만 냅니다.

## 어떻게 재나

가상 사용자 한 명을 실제 API에 차례로 넣습니다.

1. 사용자의 온보딩 답, 좋아한 책, 산 책, 취향 기억으로 프로필을 만듭니다(⑥).
2. 그 사용자의 홈 추천 위 20권을 받습니다(④).
3. 20권에 어떤 책이 몇 권 있는지를 셉니다.

프로필은 그 자체로는 좋은지 나쁜지 볼 수 없고 그 프로필로 뽑은 책을 봐야 알 수 있어서, 두 기능을 이어서 잽니다. LLM을 쓰지 않아 같은 입력이면 결과가 같습니다. 한 번만 돌리면 됩니다.

## 돌리는 법

평가용 DB(아래 "평가용 책 표")에 붙여 돌립니다. 서버를 따로 띄우지 않습니다.

```
DATABASE_URL=postgresql://localhost/bookjeok_ai_eval uv run python -m evals.feed.run            # 몇 명을 돌릴지만 본다
DATABASE_URL=postgresql://localhost/bookjeok_ai_eval uv run python -m evals.feed.run --yes      # 전부 돌린다
DATABASE_URL=postgresql://localhost/bookjeok_ai_eval uv run python -m evals.feed.run --kinds dislike,author --yes
DATABASE_URL=postgresql://localhost/bookjeok_ai_eval uv run python -m evals.feed.run --yes --out evals/feed/results/after.json
```

- `--kinds`, `--ids`, `--group`으로 사용자를 고릅니다. 짝이 있는 사용자를 고르면 짝도 같이 부릅니다.
- `--yes`가 없으면 부르지 않고 몇 명을 돌릴지만 알려 줍니다.
- 191명 전부에 1분 안쪽입니다. LLM은 부르지 않고, 취향 기억의 벡터만 로컬 임베딩 모델로 만듭니다.
- **이름이 `_eval`로 끝나는 DB에만 돌립니다.** 실행기가 가상 사용자의 프로필을 DB에 쓰기 때문입니다. 끝나면 지웁니다. 다른 DB에 돌리려면 `--any-db`를 붙입니다.
- 묶음을 만든 책 표와 권수가 다른 DB에 돌리면 결과 위에 주의가 찍힙니다.
- `--out`으로 사용자마다의 결과를 파일로 남깁니다. `evals/feed/results/` 아래에 두면 저장소에 섞이지 않습니다.

### ⑥ 시간 재기 (운영 서버)

이 실행기의 시간은 로컬 값이라 판단에 쓰지 않습니다. ⑥ 한 번이 몇 초 걸리는지는 `profile_timing.py`로 운영(또는 운영과 같은 크기·사양) 서버의 AI 컨테이너 안에서 잽니다([#492](https://github.com/100-hours-a-week/KTB4-13th-AI/issues/492)).

```
curl -fsSL https://raw.githubusercontent.com/100-hours-a-week/KTB4-13th-AI/<커밋>/evals/feed/profile_timing.py | sudo docker exec -i bookjeok-ai python - https://raw.githubusercontent.com/100-hours-a-week/KTB4-13th-AI/<커밋>/evals/feed/cases.json
```

- 이 묶음의 가상 사용자로 플래그를 켠 것처럼 ⑥을 계산하고, 저장만 건너뜁니다. 읽기 전용 트랜잭션이라 DB에 남는 것이 없습니다.
- 임베딩은 같은 컨테이너의 서버에 묻습니다. 모델을 한 번 더 올리지 않습니다.
- 뒤에 사용자 수와 건너뛸 수를 붙이면 나눠 돌립니다(예: `… cases.json 48 96`).
- 마지막 줄 `SUMMARY`에 가운데값, 90%, 최대, 3초·5초를 넘은 수, 대신 채운 관심사가 있던 사용자 수, 목록이 빈 사용자 수가 나옵니다.

## 결과 읽는 법

종류마다 한 줄입니다.

| 칸 | 뜻 |
| --- | --- |
| 가장 적게 나온 관심사 | 나와야 하는 관심사 가운데 가장 적게 나온 것이 몇 권인지. 관심사가 하나면 그 관심사의 권수다 |
| 한 권도 안 나온 관심사가 있는 사용자 | 나와야 하는 관심사 중 0권인 것이 있는 사용자 수 |

| 알 수 없는 책 | 맞는 관심사는 없는데, 세부 분류 번호가 없어 아니라고도 할 수 없는 책 |
| 시간 | 홈 추천 한 번에 걸린 시간. PC에서 잰 것이라 서버와 다르고, 종류끼리 견주는 데만 쓴다 |

- 재지 못한 사용자(API 오류, 벡터 없이 답함, 개인화 여부가 기대와 다름)는 평균에서 빼고 따로 셉니다.

- 종류를 섞은 전체 평균은 내지 않습니다.

## 무엇을 맞는 책으로 보나

사용자마다 "나와야 하는 관심사"를 적고, 관심사마다 맞는 책을 가르는 기준을 한 곳(`interests`)에 모아 두었습니다. 기준은 사람의 판단이 들어가지 않는 것을 먼저 썼습니다.

| 기준(`by`) | 맞는 책 | 쓰는 관심사 | 믿을 만한가 |
| --- | --- | --- | --- |
| `field` | 책의 분류가 그 온보딩 분야의 핵심 분류에 든다(`app/core/categories.py`) | 분야 12개 | 분류는 정확하지만 넓다. 소설 분야에는 시와 수필도 든다 |
| `kdc` | 도서관 세부 분류 번호가 그 숫자로 시작한다(예: 요리는 594) | 주제 21개 | 벡터가 있는 책의 82%에 번호가 있다. 없는 책은 "모름"으로 센다 |
| `reader` | 책의 독자 대상 부호(7은 어린이) | 어린이책 | 정확하다 |
| `author` | 저자 칸에 그 이름이 있다 | 작가 8명 | 정확하다 |
| `pages`, `pub_year`, `price` | 쪽수, 출간연도, 정가가 조건에 맞는다 | 조건 3개 | 정확하다 |
| `words` | 제목이나 소개글에 그 낱말이 있다 | 장르 4개(추리, SF, 판타지, 로맨스), 분위기 3개 | **거칠다.** "판타지"가 든 책의 절반은 판타지 소설이 아니었다 |

낱말로 가르는 관심사에는 `rough: true`를 붙였습니다. 장르와 분위기는 책의 분류로 가를 수 없어서 우선 낱말을 쓰고, 사람이 읽고 붙인 판정 모음으로 바꿀 예정입니다.

## 파일

`cases.json` 하나입니다. 사용자 한 명이 한 줄입니다.

| 칸 | 뜻 |
| --- | --- |
| `version` | 묶음의 버전. 사용자를 고치면 올린다 |
| `top` | 위 몇 권을 보는지(20) |
| `catalog` | 책을 고른 책 표. 만든 날, 책 수, 벡터가 있는 책 수 |
| `interests` | 관심사마다 이름표와 맞는 책을 가르는 기준 |
| `kinds` | 종류마다 어느 묶음(`group`)인지와 설명 |
| `cases[].id` | 사례 번호. `<종류>-<순번>` |
| `cases[].about` | 이 사용자가 누구인지 한 줄 |
| `cases[].user_id` | API에 보낼 사용자 번호. 실제 사용자와 겹치지 않는 번호대다 |
| `user.onboarding` | 고른 분야(`categories`), 세부 태그(`tags`), 좋아한 책(`liked_isbns`) |
| `user.history` | 산 책, 담은 책, 리뷰. 산 책과 담은 책은 홈 추천에도 "가진 책"으로 보낸다 |
| `user.memories` | 취향 기억. ⑤가 내는 칸(종류 `type`, 문장 `value`, 세기 `strength`, 어디에 `applies_to`, 핵심어 `keyword`)과 BE가 저장한 때(`created_at`). 묶음의 순서가 말한 순서다. 벡터는 실행기가 ⑤와 같이 핵심어로 붙인다 |
| `expect.show` | 위 20권에 나와야 하는 관심사 |
| `expect.avoid` | 나오면 안 되거나 늘면 안 되는 관심사 |
| `expect.toward` | 결과가 그쪽으로 기울어야 하는 것(분위기, 조건). 많을수록 좋다 |
| `expect.compare_to` | 견줄 짝. 마지막 취향 기억 하나만 뺀 같은 사용자다 |
| `expect.never_owned` | 가진 책이 나오면 안 된다 |
| `expect.editions` | 가진 책과 제목이 같은 다른 판본이 몇 권 나오는지도 센다. 저자는 보지 않는다(저자 칸에 옮긴이가 같이 적혀 있어 판본마다 글자가 다르다) |
| `expect.cold_start` | 개인화하지 않은 목록이 나와야 한다 |
| `expect.pile` | 좋아한 책의 권수. 권수가 같은 사용자끼리 위 20권이 겹치는 정도를 본다 |

| `topic-mood` | 주제 하나와 분위기 하나 | 주제가 남고 분위기 쪽으로 기우나 | 8 |
| `dislike` | 좋아하는 주제와 읽지 않는 주제 | 읽지 않는 주제의 책이 짝보다 늘지 않나 | 10 |
| `flip` | 같은 주제를 좋아한다고 했다가 뒤에 피함 | 마지막 말을 따르나, 이번에만 빼 달라는 부탁(세기 -1)은 좋아함을 지우지 않나 | 2 |
| `condition` | 주제 하나와 책 고르는 조건 | 조건 때문에 주제가 사라지지 않나 | 8 |
| `author` | 작가를 좋아한다고 함 | 그 작가의 책이 나오나 | 8 |
| `low-rating` | 산 책 세 권에 1점을 줌 | 그 관심사가 안 나오고 고른 분야는 나오나 | 3 |
| `owned` | 고전 한 권의 판본 셋을 가짐 | 가진 책이 안 나오나, 다른 판본은 몇 권 나오나 | 6 |
| `pile` | 서로 다른 관심사의 책을 5, 10, 20, 40권 좋아함 | 사용자마다 다른 책이 나오나 | 16 |

`condition` 가운데 "번역서는 읽지 않음"과 "오디오북으로만 들음"에는 기울어야 하는 쪽(`toward`)이 없습니다. 책 표로 가를 수 없는 조건이라 주제가 남아 있는지만 봅니다. 지금의 ⑤는 이런 조건을 뽑지 않지만, 읽을 수 없는 조건이 목록을 망치지 않는지 보려고 남겨 둡니다. 가격 조건은 "만 원 이하의 책만 삼"(세기 2)입니다. "찾음"처럼 부탁한 조건은 ⑤가 프로필에 남기지 않습니다.

`dislike`, `flip`, `condition`, `topic-mood`는 짝(`compare_to`)이 있습니다. 짝은 마지막 취향 기억 하나만 뺀 사용자라서, 두 결과의 차이가 그 기억 하나 때문에 생긴 것입니다.

## 책을 고른 규칙

사용자가 좋아하거나 산 책 437권은 평가용 책 표에서 골랐습니다. 다시 고를 때도 같은 규칙을 씁니다.

- 벡터가 있는 책만 씁니다. 벡터가 없는 책은 프로필에 아무 영향을 주지 않습니다.
- 표지가 있고, 납본됐고, 소개글이 200자 이상이고, 2012년 이후에 나온 책에서 고릅니다. 독자 대상은 교양과 실용입니다(프로그래밍, 경영처럼 전문서가 흔한 주제는 전문까지).
- 주제는 도서관 세부 분류로 고릅니다. 분류가 넓은 주제(요리, 건강 등)는 제목이나 소개글에 그 주제의 낱말이 있는 책으로 한 번 더 좁혔습니다. 좋아한 책으로 쓸 전형적인 책을 고르려는 것이고, 맞는 책의 기준은 그대로 세부 분류입니다.
- 장르 넷(추리, SF, 판타지, 로맨스)은 분류가 없어서, 후보의 제목과 소개글을 읽고 그 장르의 소설이 분명한 책만 골랐습니다.
- 책은 ISBN으로 적습니다. 책 번호는 책 표를 다시 만들 때마다 바뀝니다.

## 평가용 책 표

묶음의 책은 2026-10-13에 만든 로컬 책 표에서 골랐습니다. 책 2,107,214권이고 그중 595,329권에 벡터가 있습니다(`cases.json`의 `catalog`).

- 책: 수집한 카탈로그에서 13자리 ISBN이 있고 값이 깨지지 않은 책 전부입니다.
- 벡터: 소개글이 있는 책 가운데 "정보나루 소개글 + 표지 있음" 또는 "국중 소개글 + 납본됨"인 책에 붙였습니다. 서버의 책 벡터와 같은 모델, 같은 글로 만든 것입니다.
- 지금 쓰는 13만 권짜리 로컬 DB와는 다른 DB입니다. 책 표가 다르면 같은 묶음이어도 숫자를 견줄 수 없으니, 결과를 적을 때 어느 책 표로 쟀는지를 같이 적습니다.

만드는 순서입니다. 책 파일과 벡터 파일은 카탈로그를 수집하는 쪽에서 내보낸 것을 받습니다.

```
createdb bookjeok_ai_eval
for f in $(git ls-files db/migrations | sort); do psql -v ON_ERROR_STOP=1 -d bookjeok_ai_eval -f "$f"; done
scripts/ingest_catalog.sh <책 파일 cat_books.jsonl> bookjeok_ai_eval      # 책 211만 권, 5분
scripts/load_book_vectors.sh <벡터 파일> bookjeok_ai_eval                   # 벡터 59만 권과 색인, 4분
psql -v ON_ERROR_STOP=1 -d bookjeok_ai_eval -f evals/feed/book_classes.sql  # AI 책 분류 표, 20초
```

AI 책 분류 표(`book_classes`)는 세부 분류 번호·독자 대상·쪽수를 담은 서버의 표입니다. 실행기도 이 표로 책을 가릅니다. 평가 DB에서는 적재할 때 남은 원본 표(`stg_cat_books`)로 채웁니다(`evals/feed/book_classes.sql`). 표는 마이그레이션(`db/migrations/20261016_book_classes.sql`)이 만듭니다.

벡터 파일이 없으면 `DATABASE_URL=… uv run python -m app.jobs.embed_books`로 서버와 같은 방법으로 만들 수 있습니다. CPU로 두 시간쯤 걸리고, 소개글이 있는 책 전부에 벡터가 붙어서 위의 조건과 권수가 달라집니다.

## 한계

- 맞는 책의 기준이 관심사마다 다릅니다. 분류와 세부 분류는 믿을 만하고, 낱말은 거칩니다. 장르와 분위기의 숫자는 방향만 봅니다.
- 세부 분류 번호가 없는 책(18%)은 맞는지 아닌지 알 수 없습니다.
- 가상 사용자는 실제 사용자의 분포를 따르지 않습니다. 분야를 몇 개 고르는 사용자가 많은지는 모릅니다. 종류별 숫자를 보고, 전체를 합친 숫자는 보지 않습니다.
- 인기 점수가 책 표에 없으면 점수의 인기 항이 모두 0입니다. 운영과 순서가 다를 수 있습니다.
- 시간은 도는 순서와 PC의 상태에 따라 달라집니다. 먼저 도는 종류가 느리게 나옵니다.
- **벡터 색인을 다시 만들면 결과가 조금 달라집니다.** 가까운 책을 어림으로 찾는 색인이라, 같은 책과 같은 벡터로 다시 만들어도 후보가 한두 권 바뀝니다. 다시 만든 뒤 재 보니 187명 중 55명의 위 20권이 달라졌고(한 명당 평균 0.4권), 종류별 평균은 대개 0.2권 안쪽, 사용자가 3명뿐인 종류에서는 0.7권까지 움직였습니다. 전후는 같은 DB에서 견주고, 이보다 작은 차이는 차이로 보지 않습니다. 같은 DB에서 다시 돌리면 결과가 같습니다.
