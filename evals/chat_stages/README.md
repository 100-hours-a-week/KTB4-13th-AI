# ③ 챗봇 단계별 손실 측정

③ 챗봇(`POST /recommendations/chat`)이 질문에 맞는 책을 어느 단계에서 잃는지 재고, ③ 쪽만 바꾸는 재정렬 두 가지를 같은 숫자로 견줍니다. 이슈는 [#521](https://github.com/100-hours-a-week/KTB4-13th-AI/issues/521)입니다.

③ 평가 103문항(`evals/chat`)은 규칙을 지켰는지만 채점합니다. 질문에 맞는 책인지는 재지 않습니다. 그래서 검색을 고쳐도 나아졌다고 말할 숫자가 없었습니다. 여기서는 ① 검색 평가의 서술형 검색어 40개와 그 점수(맞음 2·조금 1·아님 0, [#502](https://github.com/100-hours-a-week/KTB4-13th-AI/issues/502))를 다시 씁니다.

## 단계

③ 첫 턴은 아래 순서로 책을 줄입니다(`app/routers/chat.py`의 `_recommend` → `get_candidates` → `generate_cards`).

| 단계 | 하는 일 | 남는 책 |
| --- | --- | --- |
| 조건 뽑기 | LLM이 말에서 조건(spec)을 뽑는다. 검색어는 `spec.semantic`(제목·저자 찾기면 제목·저자) | - |
| ① 검색 | ①의 `service.search`를 30권으로 부른다 | 30 |
| 사후 거르기 | 가진 책, 분야, 출판사, 소개글 없는 책(semantic만), 이미 본 판본, 겹치는 판본을 뺀다 | 30 이하 |
| 10권 후보 | 검색 순서대로 앞의 10권을 자른다. `match_score`는 자른 뒤에 붙는다 | 10 |
| 카드 | LLM이 10권 중 3권을 고르고 이유를 쓴다 | 3 |

## 실험

`variants.py`에서 `chat.py`의 이름 몇 개를 바꿔 끼웁니다. 앱 코드는 고치지 않습니다. 운영에 넣게 되면 `chat.py`를 직접 고칩니다.

| 이름 | 바꾸는 것 |
| --- | --- |
| `base` | 지금 그대로 |
| `rerank` (a) | 거른 뒤 남은 책 전부에 `match_score`를 먼저 매기고, 그 점수 순서로 10권을 자른다. 제목·저자 찾기(exact)는 검색 순서를 그대로 둔다 |
| `vector` (b) | intent가 semantic이면 ① 검색 대신 벡터 검색(`vector.search_ids`)으로 30권을 받는다. ①이 키워드 등수를 3배로 쳐서 흔한 낱말이 제목에 든 책이 위를 채우는 것을 피한다 |

① 검색 코드(`app/search`)는 바꾸지 않습니다.

## 결과

2026-10-19, main `95e76c1`, `openai/gpt-4o-mini`, ZDR 끔. 평가 DB는 이 PC의 10/11 사본입니다(책 2,103,860권, 벡터 467,530권). #502의 기준선을 잰 DB(벡터 595,329권)와 달라서 숫자를 그 기준선과 바로 견주지 않습니다. 같은 DB에서 원문 검색어로 ①을 다시 재면 위 10권 nDCG가 0.604입니다.

검색어마다 조건은 한 번만 뽑았고(가운데값 1.3초), 카드는 같은 후보로 3번 만들었습니다. 요청 오류, `degraded`, 벡터 검색 끊김, 점수 없는 책은 모두 0입니다.

### 한 줄 요약

**(a)와 (b) 모두 10권 후보는 조금 낫게 하지만(nDCG +0.03), 사용자가 보는 카드는 나아지지 않습니다(−0.03, 오차 안).** 카드가 나쁜 검색어는 ① 30권 안에 맞는 책이 없거나, 조건 뽑기가 말을 잘못 읽은 경우입니다. 10권을 다시 줄 세워서는 고칠 수 없습니다.

### 1. 어느 단계에서 잃나 (지금 main)

검색어 하나에 평균 몇 권이 2점(맞음)인지입니다.

| 단계 | 2점 책 / 남은 책 | 잃은 2점 책 | 뜻 |
| --- | --- | --- | --- |
| ① 검색 30권 | 12.6 / 30 | - | |
| 사후 거르기 | 11.3 / 25.9 | 1.3 | 소개글 없는 책 0.4, 같은 책의 다른 판본 0.9(일부러 뺀 것) |
| 10권 후보 | 4.7 / 9.9 | 6.6 | 10칸에 다 넣을 수 있었던 2점 책은 7.5권. 자르기에서 2.8권을 더 잃는다 |
| 카드 3장 | 1.98 / 3 | - | 카드 평균 1.71점. 10권에 있던 2점 책을 카드에 넣지 않은 것이 턴마다 0.64장 |

- **가장 많이 잃는 곳은 10권 자르기입니다.** 거른 뒤 2점 책이 11.3권 남는데, 검색 순서로 앞 10권을 자르면 4.7권만 남습니다.
- **그런데 카드는 10권에 2점 책이 3권만 있으면 대체로 괜찮습니다.** 10권에 2점 책이 3권 이상인 33개 검색어는 카드 평균 1.81점이고, 3권 미만인 7개는 1.24점입니다. 그 7개 중 6개는 ① 30권 안에 2점 책부터 3권 이하였습니다("비 오는 날 읽을 책" 0, "열등감을 … 쉬운 철학책" 0, "편의점에서 일하는 여자가 주인공인 일본 소설" 1, "수식을 … 파이썬 통계 입문서" 2, "퇴근길에 가볍게 읽을 소설" 2, "술술 읽히는 가벼운 소설" 3). 나머지 하나는 아래의 "번아웃이 왔을 때"입니다.
- **조건 뽑기는 대체로 손해가 없습니다.** LLM이 다시 쓴 검색어로 찾은 ① 위 10권은 0.612로, 원문 그대로(0.604)와 비슷합니다. 다만 40개 중 1개("번아웃이 왔을 때")를 책 제목으로 읽어(exact) 제목에 '왔을 때'가 든 책만 나왔습니다. 카드 평균은 0.50점입니다. 이 경우는 (a)·(b) 모두 손대지 않습니다.

- **(a)와 (b)는 거의 같은 책을 고릅니다.** 평가 사용자는 취향이 없어서, (a)의 `match_score`는 조건 문장과의 벡터 유사도(0.5)와 인기(0.1)뿐입니다. ①은 조건 문장처럼 긴 검색어에서는 키워드에 걸리는 책이 적어 벡터 결과와 비슷하게 줄 세웁니다. 그래서 둘 다 "벡터 순서에 가깝게" 바뀌는 것이 같습니다.
- **나아진 곳은 주제(topic)·섞인 것(mixed)입니다.** "위로가 되는 에세이"는 10권 중 2점이 5권에서 9권, "우주의 기원에 관한 책"은 7권에서 9권이 됐습니다. 하지만 두 검색어 모두 main에서도 카드가 거의 2점이었습니다.
- **나빠진 곳은 형식 조건입니다.** "따뜻한 소설"은 10권 중 2점이 3권에서 (a) 1권, (b) 0권이 됐습니다. 벡터 순서는 '따뜻한' 분위기의 에세이를 앞으로 올리고 '소설'이라는 형식을 놓칩니다. "비전공자를 위한 컴퓨터 기초"도 9권에서 7권으로 줄었습니다. 마우스 쓰는 법 같은 컴퓨터 사용법 책이 앞으로 왔습니다.
- **카드는 평균이 조금 낮지만 구간이 0을 지납니다.** 카드는 검색어마다 3번뿐이라 흔들림이 큽니다. 나아졌다고도 나빠졌다고도 말할 수 없습니다.
- **시간은 차이가 없습니다.** (b)는 키워드 검색을 건너뛰어 후보 고르기가 0.08초 빠르지만, 턴의 대부분은 LLM(조건 1.3초 + 카드 5초)입니다.

### 읽을 때 주의

- **조건은 검색어마다 한 번만 뽑았습니다.** 실험끼리 같은 조건을 쓰려고 그렇게 했습니다. 조건 뽑기가 흔들리는 정도는 이 숫자에 없습니다.
- **카드는 3번씩입니다.** 카드 평균의 차이(±0.03)는 이 정도 흔들림 안에 있습니다.
- **첫 턴, 개인화 없음만 쟀습니다.** 취향이 있는 사용자면 (a)의 점수에 취향 유사도(0.2)가 붙어 결과가 달라집니다. 여러 턴에서 조건을 좁히는 경우도 재지 않았습니다.
- **점수는 사람이 아니라 이 세션이 매겼습니다.** 아래 "매긴 점수"를 봅니다.

- #502 라벨과 맞췄습니다. 같은 책의 다른 판본인데 #502와 점수가 다르면 #502를 따랐습니다(5권). 기준을 #502의 매긴 예에 맞춰 다시 본 것이 2권입니다. 잠을 다룬 의학서는 "잠이 안 올 때 읽는 책"에 2점, 마우스 쓰는 법 같은 컴퓨터 사용법 책은 "비전공자를 위한 컴퓨터 기초"에 1점입니다.
- 사람 확인: 76권(10%)을 시드로 뽑아 `review.md`에 두었습니다. **아직 아무도 보지 않았습니다.**

## 돌리는 법

평가 DB(`bookjeok_ai_eval`)와 모델 키가 필요합니다. ③ 평가처럼 `LLM_PROVIDER`를 `openrouter`가 아닌 값으로 두어 ZDR을 끕니다(`evals/chat/README.md`의 "읽을 때 주의"). `.env`는 `source`하지 않습니다. 앱이 직접 읽습니다.

서술형 검색어와 ①의 라벨은 `evals/search/`(#502)에서 읽습니다. 다른 묶음을 쓰려면 `--search-dir`로 폴더를 줍니다.

```bash
# 1) 검색어 40개를 ③ 첫 턴으로 넣고 실험마다 단계별 책을 남긴다. 검색어마다 조건은 한 번만 뽑아 세 실험이 같이 쓰고,
#    카드는 같은 후보로 3번 만든다. 요청 400번 남짓, 이 PC 에서 45분
LLM_PROVIDER=eval-no-zdr DATABASE_URL=postgresql://localhost/bookjeok_ai_eval \
  uv run python -m evals.chat_stages.run collect \
  --out evals/chat_stages/results/run.json
```

```bash
# 2) 점수 없는 책을 매긴다. 기준은 evals/search/README.md 의 "점수 기준"
DATABASE_URL=postgresql://localhost/bookjeok_ai_eval uv run python -m evals.chat_stages.label pool \
  evals/chat_stages/results/run.json
uv run python -m evals.chat_stages.label apply --judge "누가 매겼는지, 날짜"
DATABASE_URL=postgresql://localhost/bookjeok_ai_eval uv run python -m evals.chat_stages.label review
```

```bash
# 3) 표. DB·LLM 을 부르지 않는다
uv run python -m evals.chat_stages.run report evals/chat_stages/results/run.json --cases
```

```bash
# 4) ③ 평가 103문항을 실험 쪽 서버로 돌린다(CHAT_VARIANT=base·rerank·vector)
CHAT_VARIANT=rerank LLM_PROVIDER=eval-no-zdr DATABASE_URL=postgresql://localhost/bookjeok_ai_eval \
  uv run uvicorn evals.chat_stages.serve:app --port 8001 2>&1 | tee /tmp/chat-eval-server.log
AI_SERVICE_TOKEN=… DATABASE_URL=postgresql://localhost/bookjeok_ai_eval uv run python -m evals.chat.run \
  --runs 5 --server-log /tmp/chat-eval-server.log --out evals/chat/results/rerank-raw.json
uv run python -m evals.chat.grade evals/chat/results/rerank-raw.json --save evals/chat/results/rerank.json
uv run python -m evals.chat.grade --compare evals/chat/results/base.json evals/chat/results/rerank.json
```

## 파일

| 파일 | 뜻 |
| --- | --- |
| `variants.py` | 실험 두 가지를 `chat.py`에 끼운다 |
| `run.py` | 단계별 책을 남기고(`collect`) 표를 낸다(`report`) |
| `label.py` | 점수 없는 책을 모아 가린 채점 파일을 내고(`pool`), 매긴 점수를 넣고(`apply`), 사람이 볼 10%를 뽑는다(`review`) |
| `serve.py` | 실험 하나를 건 평가 서버 |
| `labels.json` | 여기서 더 매긴 점수. 모양은 `evals/search/labels.json`과 같다. 겹치면 ①의 점수를 쓴다 |
| `review.md` | 사람이 확인할 라벨 10% |
